### 扫描出的含混点（5 簇）
1. **知识点是文件还是独立实体** —— 规格书按独立实体写（与 file 并列、单独计数、是图谱节点类型之一），但它没有容器：类型标签只有 4 种没有它，文件树 128 个文件塞不进 56 个知识点，全篇 23 处提到它但没有一处能"打开"它。
2. **演化记录的形状** —— 固定三段链 vs 事件模型。
3. **来源关系 vs 关联 两层关系被混为一谈** —— "342 条关联"这个数字含混。
4. **文件树第一层有三种分法叠着** —— 用户文件夹（笔记/项目/灵感/附件）、文件格式（md/pdf/图片/剪藏）、内容范畴（素材），三者不正交。
5. 三态缺失 / 筛选胶囊语义 / 「总结」一词双义。

### 已定案（用户答复）

**Q1 · 知识点是什么**
> 用户原话："知识点就是 AI 把用户的聊天、文件、内容整合之后的总结打上知识点标签，原始文件和总结做关联。"

→ 知识点 = **AI 的整合产出**，不是原始内容。于是划出一条关键线：
- **来源关系**（知识点 ← 素材，方向固定，蒸馏自动产生，用户不能否认）
- **关联**（AI 发现的相关性，用户可确认/否认）
两者必须拆开，不得合并计数。写进 `CONTEXT.md`。

**Q2 · 演化记录的形状**
用户选择**事件模型**，并提到"最近开源的 jev ai 很适合做这样的事情"。

→ 采用 `trigger + inputs[] + outputs[]`。写进 ADR-0001。
→ 记入 ADR 的 Consequences：`trigger` 枚举必须补齐四个 Hook（原稿漏了收集器）；卡片布局由 `inputs.length × outputs.length` 决定；`confidence` 可选；不变量 = 一次演化至少产出一个实体或一条关联（产出为空的是日志不是演化）。

### Jev 的判断（技术调研）
Jev = TypeSafe AI 的 System One 决策模型，不生成文字，直接返回带概率的结构化判定（Choice / Score / Noul）。
- **咬合点**：正好落在 `关联器`（Noul：两条相关吗）、`沉淀器`（Noul：够不够蒸馏）、`解析器`（Choice：哪一类素材）三个判断位上，与事件模型的 `confidence` / `needsConfirm` 字段天然对应。
- **关键错配**：Jev **不产出任何文字**，而沉淀器必须写出知识点正文。所以它是**决策层**，不是系统的 AI 本体。架构 = Harness 编排 + Jev（快判断）+ LLM（慢生成）。
- **约束**：官方服务未向中国大陆开放；原版权重闭源，只有云端 API；开源复现为 Open-Jev（LoRA + 决策头，基于 Qwen3.5-9B，适配器 Apache-2.0 / 代码 MIT）与 APUS 的 fast-browser-use（MIT），可本地部署。
- **风险**：Open-Jev 作者自述合成指标不构成真实校准保证 → 不能拿它的概率直接做自动路由；且素材内容是不可信输入，存在提示注入风险（Octomind 案例：注入伪造工具输出字段，把拦截决策从 0.76/0.64 打到 0.48/0.22）。
→ 未定案，作为待答问题留到下一轮。

### 调查结论

### Hermes 原语（官方文档核实）

- **home** `~/.hermes/`（Windows：`%LOCALAPPDATA%\hermes`）：`.env` / `config.yaml` / `skills/` / `memories/` / `state.db` / `profiles/<name>/` / `active_profile` / `SOUL`、hooks、plugins
- **ACP 工具集** `hermes-acp`：file（read_file/write_file/patch/search_files）、terminal（terminal/process）、web/browser、memory、todo、session_search、skills、execute_code、delegate_task、vision。**刻意排除**消息投递与 cronjob（cronjob 在 CLI 全量工具集里有）
- **技能**：`skills/<cat>/<name>/SKILL.md`，frontmatter 需 `name`+`description`；三级渐进披露（skills_list → skill_view → references）；支持 `skills.external_dirs` 外部目录
- **运行记忆**：`memories/MEMORY.md`（上限 2200 字符）+ `USER.md`（1375 字符），agent 自动写，**会话开始时冻结快照**（改了下会话才生效），超限直接报错要求 agent 自己合并；另有 8 个外部 memory provider 插件
- **会话**：`state.db`（SQLite + FTS5），全部转写，跨进程重启可恢复，`session_search` 工具做全文检索
- **约束**：一个 home 只有一个 agent，两进程指向同一 home 会互相污染记忆

### 编排分治（ADR-0002）

| 场景 | 编排者 | 形态 |
|---|---|---|
| 聊天（用户在场的开放对话） | **Hermes 自主驱动** | ACP 会话，多轮，agent 自决调哪些工具 |
| 四个 Hook（收集 / 解析 / 关联 / 蒸馏） | **我们的 Harness** | 确定性代码串联；Hermes 只在"该写字"那步被叫进来 |

原则：**不给不确定的东西以编排权**。副作用：收集器/解析器零 token——5W 弱网设备上是实打实的收益。

### 四条边界（已定）

1. **cwd 恒为知识库根**，不暴露到设置页（安全边界，不是偏好）
2. **运行记忆 ≠ 知识点**，严格分名分物（前者有硬上限、会话开始时冻结快照、用户看不见）
3. **不读 `state.db`**：对话素材作为领域实体自己存；打通方式是蒸馏时把对话内容显式喂给 agent
4. **一个 home 一个 agent** → 调用串行化，不做 per-task overlay

### 工具集白名单（硬约束）

开 `file` / `skills` / `session_search`（只读）/ `vision`（按需）；关 **`terminal`** / **`execute_code`**（素材是不可信输入）/ `web` / `browser` / `memory` / `todo` / `delegate_task`。**不照抄** multica 的 `HERMES_YOLO_MODE=1`（那是多租户方案，与我们的威胁模型冲突）。

### 模型配置（Hermes Studio 调研）

- **Hermes Studio**（`JPeetz/Hermes-Studio`，PWA）本身**只是 UI**：连 `HERMES_API_URL`（默认 `localhost:8642`）。真正的模型配置在 `~/.hermes/`
- 配置职责分离：`config.yaml`（顶级 `model` + `custom_providers[]`：name / base_url / api_key / **api_mode**）· `.env`（所有 UPPER_SNAKE 密钥）· `auth.json`（OAuth）
- 它的 onboarding 是三步：环境检查 → 模型提供商与 API Key → 密码。支持的 provider：OpenRouter / OpenAI / Anthropic / Nous Portal / 小米 MiMo / z.ai-GLM / Kimi / MiniMax / HF / 自定义端点
- **我们的差异**：不做首次向导，做**常驻设置面板**；且**两个模型位**（生成层 + 决策层）分设 —— Hermes Studio 只有一个模型位
- 写入路径优先级：优先 `hermes config set`（官方写入口），fallback 才直接改文件且**必须保留注释**（ruamel.yaml）

## 补 · 部署形态与技能下沉边界定案（ADR-0004 / ADR-0005）

用户答复两条：① Hermes 跑在设备本地「这个没问题」；② 技能下沉多少「我没太多概念」→ 由我做判断并给出解释。

### 关键发现：技能不是文档，是授权

Hermes 官方安全模型把已安装的 **skill 列为高信任载体**——原话"等价于本地主机代码，可读环境变量、可执行任意命令"；而 **MCP server 才是低信任**（子进程环境被过滤、凭据剥离、npx/uvx 包过 OSV 恶意库检查）。

→ 这条把「下沉多少」从"提示词挪个位置"重新定义成**谁拥有编排权**。ADR-0005 的核心论证即建立于此。

另外查到的两条硬事实：

- **`approvals.mode`**（`smart` / `manual` / `off`）只 gate「危险 shell 命令」，**不 gate skill**。且官方把 prompt injection 明确列为**非漏洞**（除非能绕过审批/工具集/沙箱）→ 责任全在我们这边
- 官方 SECURITY.md：**"工具级 deny list 只有在 terminal 侧有对等限制时才算真正的安全边界"** → 反过来说，**我们关掉 `terminal` 之后，其余工具级限制才真正生效**。这是 ADR-0002 白名单的额外论据

### 定案 1 · 部署形态（ADR-0004）

**与知识库同机，跑在设备本地**，不作为可配置项，**不提供"云端模式"**（两种形态会分裂 cwd 安全边界语义、上传策略、降级设计）。

- 官方最低配置 **1 vCPU / 512MB 内存 / 2GB 磁盘**，支持 ARM64；我们不做本地推理（D14）→ 正落在低配档，**技术可行**
- 4GB 总内存下 agent 要与浏览器前端共处 → **M0 验收项：实测常驻内存与冷启动**
- 推论：内存是硬预算（工具集白名单同时是内存策略）· **推理全在云端 → 三态是主路径不是异常，断网须仍可用** · 设备是单点 → 数据格式必须"离得开"

### 定案 2 · 技能下沉边界（ADR-0005）

**只下沉「怎么写」（L1），不下沉「什么时候写」。** 且因为前置问题是"这步需不需要 agent"，实际答案更干净：

| Hook | 谁判断 | 需要 agent | 技能 |
|---|---|---|---|
| 收集器 | 无人判断 | 否 | 无 |
| 解析器 | 无人判断 | 否 | 无 |
| 关联器 | 决策层（Noul） | 否 | 无 |
| 沉淀器 | 决策层 + agent | **是** | **1 个** |

**全系统只有一个技能**（沉淀器的写作规范）。四层级谱系 L0 不下沉 / **L1 只沉"怎么写"（采纳）** / L2 沉"怎么做"（越界）/ L3 全下沉（= B 方案，已否决）。

六条配套规则：① 技能正文不出现时序词 ② 触发权归 Harness（`description` 不得写成能被闲聊自主触发的口吻）③ **技能不写文件，一切写入由 Harness 执行** ④ 技能文件住 `agent/skills/`，经外部技能目录挂载，`~/.hermes/` 不进 git ⑤ 技能里不放脚本、不声明 `env_passthrough` ⑥ **不启用 agent 的"自我生成技能"**（会把未经 review 的行为定义写进高信任目录）。

→ 规则③ 直接关闭一条长期开放问题：**演化记录由 Harness 写，不由 agent 写**。

### 顺带修正一处自己先前的过头说法

早前那张 Jev 判断位图把「解析器判定素材是哪一类」也划给了决策层（Choice）。**类型是文件事实不是判断**——MIME / 扩展名 / 文件头即定；定不了标"未识别"。收回后，「解析器零 token」才真正成立，且与 CONTEXT.md「解析器不判断」自洽。

## 第二轮 · 技能命名空间拆开 + 知识空间定案（用户两问）

### 用户的第二问定了什么

原话：「我们肯定是需要允许用户通过 hermes 自由创建技能的，只是说是判断知识库是否入库让 jev 来，入库总结让 hermes 配置的大模型来」+「知识空间的概念现在有歧义的话我们就需要具体起来，和 hermes agent 的成长轨迹是否需要区别」。

**第一句没有推翻 ADR-0005，而是暴露了它的两处过度推论**：ADR-0005 要答的是"我们自己的四个 Hook 要不要把行为定义下沉成技能"（答案"只下沉怎么写"仍成立），但它顺手写下「整个系统只有一个技能」和「关闭自我生成技能」——前者把**产品拥有的技能数**错当成**系统里的技能总数**，后者等于砍掉 Hermes 的招牌能力。

**第二句的实质**：「成长轨迹」混了两个主语，必须拆开，否则会在 UI 层推翻 ADR-0002 §3 已钉死的「运行记忆 ≠ 知识点」。

### 关键论断（本次新增，可复用的思考）

1. **两个命名空间**：产品技能（1 个，住仓库，产品点名，可 review）vs 用户技能（不限，住 `~/.hermes/skills/`，agent 自主，不 review）。
2. **写入边界按作用域切**（顺带修掉一处旧矛盾）：ADR-0002 工具表把 `file` 标为 read/write，而 ADR-0005 规则 3 说"技能不写文件"——**两处矛盾**。解法：知识库根**只读**、`~/.hermes/` **可写**。一句话：**agent 可以改自己的脑子，不能改用户的资料**。这条把"技能开放"从风险变成可控项——**边界从约定升级为可测试的能力**。
3. **用户技能的自由度边界**（由用户那句话反推出来的精确表）：改得了**怎么写**；改不了**要不要入库**（决策层是独立服务，够不着）、**什么时候写**（编排在 Harness 代码里）。不靠自觉，靠能力。
4. **知识空间 ≠ profile**：知识空间是内容边界（文件树/知识点/关联/演化记录），profile 是 agent 身份（记忆/技能/config）。**默认全部空间共用一个 profile**。选 A（一对一）的硬伤：会让**每次切换空间都冷启动**，直接违反 ADR-0004 §3「常驻 gateway 是体验要求」；还会让模型配置分裂成 N 份（用户在空间 A 填的密钥在空间 B 不存在 → "设置页坏了"）。
5. **「成长轨迹」一词退役**：内容是成长 = 演化记录（进图谱）；agent 的成长 = 运行记忆 + 用户技能（不进图谱，只给存在性与规模）。理由：图谱的每一笔都必须能追溯到用户可打开的东西，而运行记忆有硬上限、会话开始时冻结、用户改不了。
6. **重载动作合并**：到 ADR-0006 为止"需重载才生效"的已有三处——模型配置 / 技能变更 / 知识空间切换——**合并为一个「重载 agent」**，设置页只出现一次。

## 第二轮 · 三态与离线降级设计（v1.1）

用户指令：「先设计侧补加载/空/错误三态」。

### 核心判断（这次设计的价值都在这里）

1. **第一原则：按「数据来源」分流，不按页面分流。** 给纯本地动作（切页/切筛选/展开文件夹）加加载态是**撒谎**——会让用户以为"这也要联网"，反而模糊降级承诺。三档：纯本地=无态 / 本地耗时=只加载 / 云端往返=完整三态+降级。
2. **「AI 正在做」是产品一等状态，不是普通加载。** 云端往返几秒到十几秒，这段时间有信息可给：三段阶段回显（读取 n 份素材 → 整合与关联 → 写知识点），**正对应演化记录的 trigger** → 聊天里看到的和进化图谱里记的是同一件事。完成后**折叠成一行痕迹**留在对话里。
3. **空态必须分四型**：E1 首次（最多 3 个并列入口）/ E2 中性（1 个）/ E3 筛选后（1 个）/ E4 搜索无果（1 个）。合并它们会导致「筛选无果」被写成「还没有内容」——**那是撒谎**。不变量：空态留在内容区内、不夺工具栏；E3/E4 必须主动说清"东西还在"（"你的 128 个文件都还在"）；E3/E4 时筛选条必须真的停在对应项上。
4. **只有 E1 允许并列动作**——那时用户任务是"知道这里能装什么"；E2–E4 是"从当前处境出去"，给多了是选择困难。
5. **错误分五型**（X1 不可达 / X2 鉴权 / X3 额度 / X4 内容 / X5 本地），一律陶色。两条铁律：**失败不毁内容**（stale-while-error，保留旧数据只挂条）、**局部失败≠整页失败**（.degrade）。
6. **离线降级是架构白送的能力**：收集器/解析器零 token（ADR-0002 编排分治）→ 离线仍可收集与浏览；聊天输入框**不锁**（草稿不丢）、发送后进**离线队列**；关联/蒸馏排队，联网自动继续。全局**只有一条**离线横幅。
7. **新建知识空间后的空 = 全套三态里最重的一处**（第二处缺口，本次闭合）。解法不是三个空白框，而是分块：树栏给轻提示 / 主区给 E1 起步引导 / **图谱页保留四个 Hook 开关与通道示意，只空掉轨迹区**——通道不是内容。

- `acp-client.ts` —— 要 **spawn `hermes acp` 子进程并持有它的 stdio**
- `spaces.ts` —— 解析知识空间根，cwd 边界就落在这里
- `model-config.ts` —— 要**读写 `~/.hermes/config.yaml` + `.env`**

浏览器**一件都做不到**（没有进程、没有文件系统、没有 stdio）。所以缺的不是一行选型，是**承载 Harness 的本地宿主**。§9.1 状态行那句"待后端形态确定"等的就是它。

### 顺带核出一处架构口径冲突

§9.1.1 原文：**「客户端 = 瘦渲染器；云端 = 编排 Harness + 决策层 + 生成层 + 索引」**——把编排划给了云端。与另外四处定案冲突：ADR-0004 §3（常驻 gateway 在设备本地 +"agent 进程要与浏览器前端共处"）、ADR-0002 §5（Harness 复用常驻 gateway）、§9.6 边界 1（cwd = 本地知识空间根）、§10.2 C（后端形态含 Hermes 运行时）。

**判断**：那句是 v1.0（D14 时代）写的，用的是"客户端 / 云端"两分法，早于"设备本地 / 公网"这套更细的分层；ADR-0002/0004 定案后没人回头改。四处对一处，**改的是一处**。

同一张表里还有第二处错位：把「全文检索、图谱布局与聚合」也划给云端，而 §6.2 的三态分档把「**全库搜索**」「**重排图谱**」明确归为**本地有耗时**（只给骨架、不出网）。按 §6.2 改——检索与布局留在本地，只有需要模型的 embedding 计算出网。

### 定案（用户拍板两条）

1. **先补文档口径，再搭 M0**
2. **宿主形态 = 本地 Node 守护进程 + 浏览器**（否决 Tauri / Electron：Electron 常驻 150MB+ 撞 4GB 硬预算；Tauri 在 ARM64 上多一层 Rust 工具链与系统 webview 的验证成本，而不解决任何已在问题里的事）

### 关键论断

- **三个根，各有各的运行时**：`src/`（浏览器产物）· `agent/`（宿主进程，**顶层，不在 `src/` 下**）· `shared/`（共用类型）。ADR-0005 规则 4 与 ADR-0006 引用的本就是**顶层** `agent/skills/` 与 `agent/harness/`——§9.3 把它们嵌进 `src/` 是个笔误级的错位，**正是它让"宿主在哪"变得看不出来**
- **宿主是知识空间唯一的写入者**：agent 运行时是它拉起的**子进程**。ADR-0005 修订说的"演化记录由 Harness 写"由此**从约定升级为能力**——agent 连写权限都没有
- **M0 的产出随之改变**：不再只是"能切 5 个空页面"，而必须**把双进程拓扑立起来**（浏览器 → localhost → 宿主）。晚一步做会返工：M5 要重搭一遍通信层
- **内存实测口径改为两进程之和**（宿主 + Hermes）——宿主自己也进预算，这是本 ADR 唯一新增的待验证风险
- **术语收口**：`Harness` 在全部文档里用了 20+ 次却从没进过 `CONTEXT.md`。补 **Harness** 与 **本地宿主** 两条术语，并明确三者不得混用（Harness = 编排层 / 本地宿主 = 承载它的进程 / agent 运行时 = 它拉起的子进程）
- **新增一条未定**：用户可见的 `gateway` 字样指谁。文档叙述里它一直指 agent 运行时，但 §6.3.3 的 X1 文案把它印在**用户看得见**的技术细节行；宿主引入后出现第三个候选

### 工具教训

- `python` 在本机**不在 PATH**，要用 **`py`** 启动器；校验器必须给**正确参数**——`context_md_linter.py` 收 CONTEXT.md 的路径、`adr_scanner.py` 收 `docs/adr` 目录；传 `.` 会报 PermissionError 或把根目录的 md 当 ADR 扫
- **`open_result_view` 只接受工作区内的路径**：报告写到 `<appDataDir>/brain/<id>/` 会被拒，得落到工作区里
