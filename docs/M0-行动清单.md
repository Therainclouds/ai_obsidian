## 5 · 关于方案本身的一点判断

**够硬的部分**：32 条决策记录（D1–D32）· 8 条 ADR · 26 个术语 + 三套自动校验器 · 一条不变量贯穿（"产出为空的是日志不是演化"）。
这个密度在个人项目里不常见，最大的收益是**每次定案都留了"为什么否决另外两条路"**——ADR-0008 能一次写完五个候选，靠的就是前面五条 ADR 已经把边界钉死了。

**开始变成成本的部分**：文档规模已经越过"人读得过来"的线，于是**内部互不一致开始出现**。
本次一次巡检就捞到 **3 处口径冲突**（§9.1.1 的「云端 = 编排 Harness」旧句 / 同表把「全文检索、图谱布局」划给云端 / §10.2 B 的布局坐标），全靠人肉 grep 才发现——其中第一处已经卡住了 M0。

→ **M0 起把「文档-代码一致性」交给校验器**：`glossary_code_consistency.py` 已就位，但它"有代码后才有意义"，正好是现在。别再靠人读。

**另一条**：设计阶段的纪律（先原型 → 再规格 → 最后代码）**到代码阶段要反过来一点**——现在有 122 KB 规格书对 0 行代码，继续按文档驱动的节奏走，会把"没验证过的假设"写得更厚。**M0a 那两件事的价值就是把假设换成事实。**
