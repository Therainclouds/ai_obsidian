# 宿主进程跑在设备本地，浏览器只做渲染

规格书 §9.1 的技术栈只列了前端：React + Vite + TypeScript + Tailwind + shadcn/ui + Magic UI。但同一份文档的 §9.3 又把下面三样放在 `src/` 下：

- `acp-client.ts` —— **拉起 `hermes acp` 子进程并持有它的 stdio**
- `spaces.ts` —— 解析知识空间根，而 cwd 边界就落在这里（ADR-0002 §2 / ADR-0006）
- `model-config.ts` —— **读写 `~/.hermes/config.yaml` + `.env`**（ADR-0003）

这三件事，浏览器**一件都做不到**：没有进程、没有文件系统、没有 stdio。所以 §9.1 少的不是一行选型，是**一整层**——承载 Harness 的本地宿主。§9.1 状态行那句"待后端形态确定"等的就是它。

更早的一处旧句则给出了相反的答案。§9.1.1 原文：

> **架构形态**：客户端 = **瘦渲染器**（渲染 + 本地缓存 + 交互）；云端 = 编排 Harness + 决策层 + 生成层 + 索引。

这是 v1.0（D14 时代）写下的：当时"客户端"指设备、"云端"指整个后端。但 ADR-0002 与 ADR-0004 在这之后把编排权与 agent 运行时刻意钉回了设备本地——**四处定案对一处旧句**。旧句留着，M0 就无从搭起。

## 定案

**本地宿主 = 一个 Node 常驻进程，跑在设备本地（与知识空间同机，ADR-0004）；浏览器只做渲染。**

| 层 | 跑在哪 | 职责 |
|---|---|---|
| **渲染器** | 设备上的浏览器 | 渲染、本地缓存、交互。**没有文件系统、没有进程** |
| **本地宿主** | 设备本地，Node 常驻 | Harness（四个 Hook 的确定性编排）· ACP 客户端（stdio）· 前端产物托管 · 本地索引 · **知识空间的唯一写入者** |
| **agent 运行时** | 设备本地，宿主拉起的**子进程** | Hermes（`hermes acp`）。持模型配置、持会话、做工具循环 |
| **决策层 / 生成层** | 云端 | 判断与写字。**只有算力在云端，编排不在** |

前端与宿主之间**只有一条通道**：`localhost` 上的 **HTTP + SSE**（SSE 单向流式，正是 §6.3.1 三段阶段回显要的形状）。

**为什么宿主是一个独立进程，而不是与渲染器同进程**：渲染器必须是浏览器（ADR-0004 §6 的验收项写的就是"浏览器前端同时开启"），而浏览器不可能 spawn 子进程或碰文件系统。同进程要成立只能改渲染器的形态（Tauri / Electron），那两条已在下文否决。

## Considered Options

- **A · 本地 Node 宿主 + 浏览器（采纳）** —— 内存最省；`hermes acp` 是 stdio 协议，Node 侧持有子进程是天生的；前端产物由同一个进程托管，不需要第二个服务。ADR-0004 §6 的验收项本来就是按"浏览器前端同时开启"写的。
- **B · Tauri 桌面壳** —— 否决。确实能拿到进程与文件系统权限，但它在**渲染器与宿主之间多插一层 Rust**，而这一层不解决任何已在问题里的事；代价是要在 ARM64 目标机上验证一整套 Rust 工具链与系统 webview 的可用性。在 4GB / 单核≈140 的设备上，这份验证成本换不来收益。
- **C · Electron** —— 否决。常驻 150MB+，直接撞 ADR-0004 §1「内存是硬预算」；而 ADR-0004 §1 还写明「白名单之外不再装依赖」。
- **D · 宿主也放云端（= §9.1.1 旧句）** —— 否决，且是最该否决的一个：Harness 若在云端，它就无法以本地路径为 cwd、无法写设备上的演化记录、无法读 `~/.hermes/config.yaml`。**ADR-0004 的整条论证都会随之瓦解**——那条 ADR 存在的理由就是"素材与知识空间不离开设备"。
- **E · 前端直连 ACP** —— 不可能。ACP 是 JSON-RPC over **stdio**，浏览器没有 stdio。

## Consequences

### 1 · 它修掉 §9.1.1 的一处旧句

「云端 = 编排 Harness + 决策层 + 生成层 + 索引」→「设备本地 = 渲染器 + 本地宿主 + agent 运行时；云端 = 决策层 + 生成层」。

顺带暴露同一行表里的第二处错位：§9.1.1 把「全文检索、图谱布局与聚合」也划给了云端，而 §6.2 的三态分档把「**全库搜索**」「**重排图谱**」明确归为**本地耗时**（只给骨架、不出网）。两处不一致，按 §6.2 改——**检索与布局留在本地**，只有需要模型的 embedding 计算出网。

### 2 · 「知识空间的唯一写入者」从约定变成物理事实

ADR-0005 修订后说「演化记录一律由 Harness 写，不由 agent 写」，靠的是给 Hermes 关掉 `file` 的 write/patch。宿主定案后这条更硬了一层：**宿主是设备上唯一持有知识空间写权限的进程**，agent 只是一个被它拉起的子进程。

### 3 · M0 的产出随之改变

M0 不再只是"能切 5 个空页面"，而必须把**双进程拓扑立起来**：浏览器 → localhost → 宿主，宿主托管前端产物。空的路由层即可，**不接 ACP**（ACP 在 M5）。晚一步做会返工：前端与后端若一开始不在同一个拓扑里，M5 要重搭一遍通信层。

### 4 · 状态管理的选型解除挂起

§9.1 原来写"Zustand 或 TanStack Query（视数据来源定）"。宿主定案后数据源单一（宿主 API），**TanStack Query 管服务端状态、Zustand 管 UI 状态**（主题 / 当前空间 / 小窗开合）。

### 5 · 宿主进程本身进入内存预算

ADR-0004 §1 说内存是硬预算、ADR-0004 §6 要求实测 Hermes 常驻内存。现在预算里**多了一个 Node 宿主**——所以 M0 的实测项改成测**两个进程之和**，且必须与浏览器同时开启。这是本 ADR 唯一新增的待验证风险。

### 6 · `agent/` 是顶层目录，不在 `src/` 下

ADR-0005 规则 4 写的是「技能文件住 `agent/skills/`」、ADR-0006 写的是「`agent/harness/` 维护空间解析」——两处指的本来就是**仓库顶层**。§9.3 把它嵌进 `src/` 是个笔误级的错位，正是它让"宿主在哪"变得看不出来。本 ADR 明确：`src/` 是浏览器产物、`agent/` 是宿主进程、`shared/` 是两者共用的类型。

### 6.1 · 通道选型复核（2026-09-28 · 依据「通道直接走最稳定的」）

**结论：维持 stdio + HTTP/SSE 不变**，并把理由补全：

| 段 | 选型 | 否决的候选 | 理由 |
|---|---|---|---|
| 宿主 ↔ agent 运行时 | **stdio JSON-RPC（ACP）** | TCP/IPC bridge broker | broker 解决的是**多方共享一个 agent**。我们只有一个宿主、一个 agent，多一层 broker 只多一类故障（端口占用 / socket 残留 / 鉴权面）。stdlib 还自带"子进程生命周期绑定父进程"，正好满足"一个 home 一个 agent" |
| 渲染器 ↔ 宿主 | **HTTP + SSE** | WebSocket / Socket.IO | 我们只需要**单向流**；`EventSource` 内建自动重连，无 upgrade 握手，零新依赖。Socket.IO 面向的是 Web 终端 PTY + 群聊 + 多 agent 并发流那种场景，不是我们的形状 |

**唯一会推翻这个选择的情形**：出现真正的双向高频交互（如小窗与主聊天并发流 + 需要**中途打断生成**）。届时换的是同一通道两端，接口形状不变。

> 参考对象 `EKKOLearnAI/ekko-studio`（原 Hermes Studio，11.2k star）在上述两处都与我们不同 —— 差异原因与逐条对照见 `docs/接口规范.md` §5。它的**分层依赖规则**被我们采纳。

### 7 · 尚未定

- **用户可见的 `gateway` 字样指谁**：§6.3.3 的 X1 文案里有 `gateway · upstream_timeout`，而文档叙述中的"gateway"一直指的是 agent 运行时（ADR-0006 的"切空间要换一个 gateway"）。宿主引入后出现了第三个候选。这条留待设计侧收口，不在本 ADR 内决断。
- **宿主是托管前端产物还是由独立静态服务托管**：本 ADR 按"同一个进程托管"定，理由是省一个常驻进程；若后续实测出现端口/权限冲突再议。

## 后续修订（2026-09-28 · ADR-0009）

**本 ADR 的"渲染器形态"被推翻，「分层」被保留。**

- **推翻**：Considered Options 里 A（浏览器）与 C（Electron）的取舍错了。当时否决 Electron 的理由是"常驻 150MB+ 撞内存硬预算"，可**浏览器也是 Chromium、也是 150MB+**，而本 ADR §5 自己承认浏览器进预算——同一把尺子量两边，Electron（主进程即宿主）反而少一个 Node 进程。让旧方案划算的唯一前提是"那台设备本来就要开浏览器"，而目标是**专用设备**，前提不成立。
- **推翻**：上文"渲染器必须是浏览器（ADR-0004 §6 的验收项写的就是'浏览器前端同时开启'）"是**循环论证**。ADR-0004 §6 那句是**测量场景**，不是形态规定，把因果反过来了。
- **取代**：Considered Options B（Tauri）的否决理由改判——不是因为它差，而是它**解决不了本案要解决的事**：宿主要么翻译成 Rust（重写 `acp-client` / `spaces` / `model-config`），要么打 Node sidecar（**仍然是两个进程**）。详见 ADR-0009。
- **保留且升值**：Consequences 2（宿主是知识空间唯一写入者）、3（子进程拓扑）、6（`agent/` 是顶层目录）。**正是因为宿主逻辑收在一个根里，换壳的成本才被限制在"入口 + 传输"两处、约 150 行**——ADR-0009 能这么便宜地推翻本 ADR，靠的就是本 ADR 的分层。
- **并入 ADR-0009 的**：§6.1 里"唯一会推翻 HTTP/SSE 的情形"（双向高频 + 中途打断生成）**被 IPC 天然满足**，该悬置项关闭，WebSocket 不会再出现。
