# 四个 Hook 只下沉「怎么写」，不下沉「什么时候写」

> **范围**：本 ADR 讨论**产品技能**——我们随版本发布、由产品代码点名调用的技能。**用户技能**（用户或 agent 自己在运行时 home 里创建的）是另一个命名空间，见文末「修订（2026-09-23）」。正文出现的"技能"一律指产品技能。

四个 Hook 的行为定义**只有"质量标准与输出契约"下沉到技能**；"什么时候写、按什么顺序写"留在 Harness。实际下沉量比这个问题听起来小得多：**产品侧只有一个技能——沉淀器的写作规范。**

## 为什么技能不是"文档"而是"授权"

Hermes 的官方安全模型把已安装的 skill 列为**高信任载体**，原话是"等价于本地主机代码，可读环境变量，可执行任意命令"。而 MCP server 才是低信任（子进程环境被过滤、凭据剥离）。

这条事实改变了问题的性质：往 `SKILL.md` 里放东西**不是把提示词挪个地方，是把一部分控制权交给一份住在另一个项目地盘上、我们不 review 的文件**。所以"下沉多少"等于在选：**谁拥有这件事的编排权。**

## 前置问题：这一步需不需要 agent

"要不要下沉"之前先问"需不需要 agent"。四个 Hook 的答案：

| Hook | 谁做判断 | 需要 agent | 技能 |
|---|---|---|---|
| 收集器 | 无人判断 | 否 | 无 |
| 解析器 | 无人判断 | 否 | 无 |
| 关联器 | 决策层（Jev 类） | 否 | 无 |
| **沉淀器** | 决策层（够不够蒸）+ agent（写正文） | **是** | **1 个** |

收集器与解析器不进模型；关联器做判断但不写字，判断由决策层承担。**只有沉淀器需要写字，因此只有一份技能。**

> 顺带修正：早先把"解析器判定素材是哪一类"也划给了决策层，这是过头了。**类型是文件事实，不是判断**——MIME / 扩展名 / 文件头即可确定；确定不了的标"未识别"，不外呼模型。修正之后 ADR-0002 那句"解析器零 token"才真正成立。

## Considered Options

| 层级 | 下沉什么 | 谁决定时序 | 判定 |
|---|---|---|---|
| **L0 不下沉** | 技能里什么都不放，提示词写在 Harness 代码里 | Harness | 可行，但失去渐进披露，提示词与代码混在一起 |
| **L1 下沉"怎么写"（采纳）** | 质量标准 + 输出契约 | **Harness** | ✅ |
| **L2 下沉"怎么做"** | 步骤序列（先读 A 再读 B） | 部分交给 agent | ✗ 侵蚀 ADR-0002「不给不确定的东西以编排权」 |
| **L3 全下沉** | 四个 Hook 各一个技能 | agent 自主 | ✗ 即 ADR-0002 的 B 方案，已否决 |

L2 被否决的实质理由：步骤序列一旦住进技能，**"读哪些、读多少、什么时候停"就变成 LLM 的即时决定**。而且多轮工具调用 = 更多 token 与往返，在低配设备上是直接成本。

## 五条配套规则

1. **技能正文里不出现时序词**（"先…再…然后…"）。出现时序词即视为越界。
2. **触发权归 Harness**：技能由 Harness 显式点名调用。`description` 不得写成会被 agent 在闲聊里自主触发的口吻——否则一次普通对话就可能触发一次蒸馏，**演化记录在我们的事务边界之外产生**。
3. **技能不写文件。** agent 只用 `file` 读；**一切写入（知识点文件、来源关系、演化记录）由 Harness 执行**。这条最硬：即使 agent 自主触发了技能，它也没有能力污染知识空间。
4. **技能文件住在我们仓库**（`agent/skills/`），经 Hermes 的外部技能目录挂载。`~/.hermes/` 不进 git、不是产品的一部分——产品逻辑住在那儿，就不可 review、不可回滚、不可 audit。
5. **技能里不放脚本、不声明 `env_passthrough`**，纯 markdown 提示词。因为技能是高信任载体，一个能读环境变量的技能等于把密钥面打开。

## Consequences

### 1 · 「演化记录由谁写」就此钉死

**由 Harness 写，不由 agent 写。** 这条原本是本 ADR 的开放问题，现在由配套规则 3 直接关闭。§5.2 里"演化记录由谁产生"不再待定。

### 2 · 三个 Hook 零 token

收集器、解析器、关联器都不进 agent。代价是**关联器的判断质量完全取决于决策层的校准**——延续 ADR-0001 的约束：凡要写入图谱的动作，`confidence` 阈值之外必须另有一道确定性检查。

### 3 · 提示词迭代不必动 Hermes，但需要重载

改 `agent/skills/*.md` 即改行为。但技能在会话建立时加载，**改完需要重载 agent**——与 ADR-0003 的"改配置需重启"是同一类生效条件，设置页若要暴露"重载"动作，两者应合并成一个。

### 4 · 不复用 Hermes 的"自我生成技能"

> ⚠️ **本节结论已被文末「修订（2026-09-23）」撤销**，保留原文以存证。撤销后的规则是"另立命名空间并隔离"，不是"关闭该特性"。

Hermes 的招牌特性之一是 agent 能从任务中**自动生成可复用技能**。在本产品里这必须**关闭或忽略**：它会把未经 review 的行为定义写进高信任目录。这是新识别出的硬约束，实现时需确认是否有配置开关（待验证）。

## 修订（2026-09-23）：用户技能另立命名空间

原版有两处过度推论，被用户否掉，此处撤销。用户立场（原话）：

> "我们肯定是需要允许用户通过 hermes 自由创建技能的，只是说是判断知识库是否入库让 jev 来，入库总结让 hermes 配置的大模型来。"

### 撤销一 · 撤销「整个系统只有一个技能」

原话把**产品拥有的技能数**错当成了**系统里的技能总数**。撤销后立**双命名空间**：

| | **产品技能** | **用户技能** |
|---|---|---|
| 谁写 | 我们，随版本发布 | 用户或 agent 自己 |
| 住哪 | 产品仓库 `agent/skills/`（经外部技能目录挂载） | 运行时 home `~/.hermes/skills/` |
| 谁触发 | 产品代码**点名** | agent 自主（含闲聊中） |
| 数量 | 1（沉淀器的写作规范） | 不限 |
| 产品是否 review | 是：进 git、可回滚、可 audit | **否** |
| 界面上 | 只读展示 | 可见、可启用 / 停用、可编辑 |

**正文的五条配套规则全部只约束产品技能。** 用户技能不受"不出现时序词""description 不得写成会被自主触发的口吻"约束——那两条是为 Harness 点名调用服务的前提，对用户技能没有意义。

### 撤销二 · 撤销「关闭自我生成技能」（原规则 6）

原规则 6 要求关闭 Hermes 的自我生成技能，理由是"会把未经 review 的行为定义写进高信任目录"。**撤销**——那正是用户要的能力。

取而代之的是一条**边界**，而不是一条禁令：

> **agent 可以改自己的脑子，不能改用户的资料。**

### 修订三 · 写入边界改按作用域切（原规则 3 的修订）

原规则 3 说"技能不写文件"，但 ADR-0002 的工具表里 `file` 标的是 read/write/patch/search —— **两处矛盾**。原规则靠约定，新规则靠**工具能力**：

| 作用域 | 权限 | 谁写 | 理由 |
|---|---|---|---|
| **知识空间根**（随空间切换） | **只读**（read / search） | 只有 Harness | 演化记录、知识点文件、来源关系由确定性代码写——这条不因技能开放而放松 |
| **运行时 home**（`~/.hermes/`） | **读写** | agent 自己 | 用户技能与运行记忆是 agent 自己的能力，本就该它自己长 |

由此 ADR-0002 的工具表需要修订：**`file` 的 write / patch 关闭**，只留 read / search。

> 这条修订同时让"技能开放"变得安全：**用户技能即便想污染知识空间，也没有工具。** 安全边界从"一份我们不 review 的 markdown 里写了什么"，变成"agent 手里有没有写权限"——后者是可验证、可测试的。

### 用户技能的自由度边界

用户的第二个分句给出了精确答案。用户技能能改的**只有一件事**：

| 环节 | 谁定 | 用户技能能改吗 |
|---|---|---|
| **要不要入库**（相关不相关、够不够蒸） | **决策层**（Jev 类） | 不能——那是独立服务，技能够不着 |
| **什么时候写、按什么顺序写** | **Harness** | 不能——编排在产品代码里，不在技能里 |
| **怎么写**（质量标准、输出契约） | 生成层读技能 | **能** ← 用户技能的全部作用域 |

这条边界不靠自觉维持，靠**能力**维持：决策层是另一个服务的调用，Harness 的时序在代码里，两者都不在技能的可影响面上。

### 新增 · 用户技能的风险必须写在界面上

Hermes 官方把 skill 定性为**高信任载体**——"等价于本地主机代码，可读环境变量，可执行任意命令"。放开自建之后，用户会从各处复制技能进来。因此产品有三件事必须做：

1. **标记来源**：「技能」面板把产品技能与用户技能**分区展示**，用户技能标"你自己添加的，系统不保证"
2. **拦截脚本面**：带可执行脚本或声明 `env_passthrough` 的技能**默认拒绝加载**，并说明原因——`terminal` / `execute_code` 已在工具集层关闭，但技能层的脚本声明是另一条路径
3. **告知 token 成本**：用户技能的 `description` 由 agent 自主匹配，可能被闲聊触发。它**改不了知识空间**（写入边界兜住），但会消耗云端推理的 token——在按量计费的模型上是真金白银。面板须写明并提供一键停用

> 原规则 5"技能里不放脚本、不声明 `env_passthrough`"由此**升级适用范围**：对产品技能是自律，对用户技能是**校验**。

### 未变的结论

- 四个 Hook 的分工不变：只有**沉淀器**需要 agent 与技能
- **演化记录仍由 Harness 写**——这条由修订后的作用域边界重新保障，且比原版更硬：原来是约定，现在是能力
- **产品技能仍住在产品仓库**，`~/.hermes/` 仍不进 git、不是产品的一部分
- §3 的"改技能需重载 agent"成立，并与模型配置、知识空间切换**合并为一个重载动作**（见 ADR-0006）
