# 渲染器是桌面应用，宿主并入主进程，通道换 IPC

ADR-0008 刚定下「本地 Node 宿主 + 浏览器」。这条 ADR 推翻它的**渲染器形态**，保留它的**分层**。

## 为什么要推翻

### 1 · 它否决桌面壳的两条论证本身站不住

ADR-0008 的第一条（原文第 30 行）：

> **为什么宿主是一个独立进程，而不是与渲染器同进程**：渲染器必须是浏览器（ADR-0004 §6 的验收项写的就是"浏览器前端同时开启"），而浏览器不可能 spawn 子进程或碰文件系统。

这是**循环论证**。ADR-0004 §6 那句是**测量场景**——要求测内存时把浏览器也开着，因为那才是真实占用；它甚至在下一句写明浏览器是一笔要交代的额外成本（"若超出预算，可退的空间是'前端与 agent 不同时重载'"）。**把测量假设当成设计约束，是把因果反过来了。** 正确的顺序是：先定渲染器形态，再按它决定怎么测。

### 2 · 它否决 Electron 的内存理由，对自家采纳的方案同样成立

ADR-0008 否决 C（Electron）的理由是「常驻 150MB+，直接撞 ADR-0004 §1 的内存硬预算」。**可浏览器也是 Chromium，也是 150MB+。** 而 ADR-0008 §5 自己承认浏览器进预算（"必须与浏览器同时开启"）。同一把尺子量两边：

| 方案 | 组成 | 粗估常驻 |
|---|---|---|
| **旧 A · 浏览器 + 宿主** | Chromium 150–300MB ＋ Node 宿主 40–60MB | **约 190–360MB** |
| **新 A · Electron** | Chromium 150–300MB（**主进程就是那个 Node 宿主**，不必再加一个） | **约 150–300MB** |

**唯一让旧方案划算的前提是"那台设备本来就要开浏览器"。** 目标机 RK3528 是**专用设备**（用户已确认：开机就是这个系统，平常用不到浏览器），这个前提不成立。于是旧方案在专用设备上**多花一个 Node 进程的内存，还换来一个更差的产品**——用户要开浏览器、敲地址。

> 数字都是数量级判断，不是实测。真正的数字由本文 Consequences 1 的实测给出。

### 3 · 产品形态本身就是错的

一个"个人知识系统"如果运行形态是一个标签页，那么：它没有自己的窗口、没有开机自启、关掉浏览器就等于关掉产品、用户要记住一个地址。**专用设备上的产品应该是一个应用。**

## 定案

**渲染器 = Electron 应用；Electron 主进程 = 本地宿主；渲染器与宿主之间走 IPC，不再有 localhost HTTP。**

| 层 | 形态 | 职责 |
|---|---|---|
| **渲染器** | Electron 渲染进程（Chromium），`nodeIntegration: false` · `contextIsolation: true` | 渲染与交互。**仍然没有文件系统、没有进程** |
| **本地宿主** | **Electron 主进程**（Node） | Harness · ACP 客户端（stdio）· 本地索引 · **知识空间的唯一写入者** |
| **通道** | **`contextBridge` 白名单 IPC**（preload 暴露 `window.host`） | 取代 HTTP + SSE。**同一个应用内的进程间通信** |
| **agent 运行时** | 宿主拉起的子进程 | Hermes（`hermes acp`）—— 这一层**完全不变** |
| **决策层 / 生成层** | 云端 | 不变 |

**`agent/` 那 510 行一行都不用重写。** 变的是它的入口（不再起 HTTP server）与传输层（`http.ts` 换成 ipc），业务在 `services/`、协议在 `acp-client.ts`，都不动。

## Considered Options

- **A · Electron（采纳）** —— 主进程天然是 Node，现在 `agent/` 的东西直接搬；官方发布 **linux-arm64 预构建**，不需要交叉编译；只加 `electron` 一个依赖，符合 ADR-0004 §1「白名单之外不再装依赖」。**而且它删掉的东西比加的多**：不再需要 localhost HTTP 服务（端口 / 静态托管 / CORS / EventSource）与 `static.route.ts`。
- **B · Tauri** —— 否决，但不是因为它差。它在**运行时可能最省**（Linux ARM64 走 WebKitGTK，通常轻于 Chromium），磁盘占用也小得多。否决理由是**它解决不了本案要解决的事**：宿主那一层要么翻译成 Rust（等于把刚定案的 `acp-client` / `spaces` / `model-config` 全重写，并丢掉 Node 侧现成的 ACP stdio 支持），要么打一个 Node sidecar——**那就仍然是两个进程，而这次的目的正是不再是两个东西**。附带成本：目标机需装 Rust 工具链 + webkit2gtk 开发包并原生编译，且运行期绑定发行版的 WebKitGTK 版本，在专用设备上是真实的验证风险。
- **C · 维持浏览器 + 宿主（= ADR-0008 的 A）** —— 否决。理由见上：专用设备上浏览器不是白送的，而产品形态是一个标签页。
- **D · 渲染器直连 ACP** —— 仍然不可能。ACP 是 JSON-RPC over **stdio**，渲染进程没有 stdio。宿主这一层无论用什么壳都省不掉。

> **如果 ARM64 实测显示 Electron 超出预算**：Tauri 是退路。而这条退路之所以便宜，正是因为 ADR-0008 把宿主逻辑收在 `agent/` 一个根里——**换壳的成本被限制在"入口 + 传输"两处，约 150 行**。这是 ADR-0008 真正的遗产：它选项判断错了，但分层是对的，所以这次改的只是壳。

## Consequences

### 1 · M0 的内存实测口径第三次改写，并且变得更干净

| 版本 | 口径 |
|---|---|
| ADR-0004 §6（原始） | 实测 **Hermes 进程**常驻与冷启动，浏览器同时开启 |
| ADR-0008 §5 | 实测 **宿主 + Hermes 两个进程之和**，浏览器同时开启 |
| **本 ADR** | 实测 **Electron 应用（主进程 + 渲染进程，含全部辅助进程）＋ Hermes** |

**ADR-0004 §6 那句"必须在浏览器前端同时开启的场景下测"作废。** 它的用意是"别漏算渲染器的开销"——现在渲染器本来就在被测的进程树里，所以这条要求从"额外的注意事项"变成了"自然的组成部分"。**口径反而更严了**，因为以前那个"同时开启"只是口头约束，现在是同一个应用。

### 2 · 删掉一整层：localhost HTTP

不再需要的：端口分配（`shared/ports.ts`）、静态产物托管（`agent/routes/static.route.ts`）、CORS、`EventSource` 的自动重连、以及那份"前端与后端之间有一条网络通道"的心智模型。

**渲染器仍然不能碰文件系统与进程**（`nodeIntegration: false` + `contextIsolation: true` + preload 白名单），所以 ADR-0008 §2「宿主是知识空间唯一写入者」继续成立，而且更硬：白名单在 preload 里显式列出，渲染器连"随便发一个请求"的能力都没有。

### 3 · 「唯一会推翻 HTTP/SSE 的情形」直接被满足

ADR-0008 §6.1（今天刚补的）写：

> **唯一会推翻这个选择的情形**：出现真正的双向高频交互（如小窗与主聊天并发流 + 需要**中途打断生成**）。届时换的是同一通道两端，接口形状不变。

IPC 天生双向、天生有推送，**这两个需求不用等就满足了**。所以那条"以后可能要换 WebSocket"的悬置项一并关闭——WebSocket 不会再出现。

### 4 · 接触面只有 3 个端点，迁移成本小

当前渲染器 → 宿主的全部接触面：

| 位置 | 现在 | 改成 |
|---|---|---|
| `src/lib/useHostHealth.ts` | `fetch('/api/health')` | `window.host.invoke('health')` |
| `src/features/chat/index.tsx` | `fetch('/api/agent/status')` | `window.host.invoke('agent.status')` |
| `src/features/chat/index.tsx` | `fetch('/api/agent/chat')` | `window.host.stream('agent.chat', …)` |

`agent/` 侧：`routes/*.route.ts` 的处理器逻辑保留，换传输；`lib/http.ts` 与 `http.ts`（共 107 行）删除，换成 ipc 注册；`static.route.ts` 删除。

### 5 · 开发形态

- **开发**：Electron 窗口加载 `http://localhost:5173`（Vite dev server，HMR 照旧）；通道仍是 IPC
- **生产**：窗口加载 `dist/index.html`；不再监听任何端口

### 6 · 需要回头核的地方（本次不擅改）

- ~~**§6.3.3 的 X1 文案里有没有"浏览器"字样**~~ → **已核：没有**。全篇 `浏览器` 只出现在 §9.1 / §9.3 / §9.6 / §10 这几处讲架构的地方，都已随 v1.5 改过。留一条纪律：**今后新写的界面文案不得再说"浏览器"**——那对用户不是可指的东西了
- **`gateway` 那条待定项没被解决**：宿主从"独立进程"变成"主进程"，候选反而更好分辨了（用户可见的那个词更可能是 agent 运行时），但仍需设计侧收口
- **`docs/接口规范.md` §2** 整节（通道选型）要重写；§1 的架构图要改
